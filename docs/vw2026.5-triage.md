# VW2026.5 Regression — Triage Notes

**Status:** open investigation, 2026-05-26
**Branch:** `claude/lattice-platform-mcp-TM9xi`
**Trigger:** plugin instability (full VW crashes, possible BSODs) reported on VW2026 after Update 5 installed. Not yet directly reproduced against this fork's `vectorworks-mcp.vlb`, but the regression pattern is consistent with public reports and worth a structured triage.

## 2. Working hypotheses (ranked)

Ordered by how well each explains the symptoms + public reports.

### H1 — Credential enforcement tightened in U5 (high prior)
- **Mechanism:** VW2026.0–2026.4 reported unsigned plugins via dialog but still loaded them (we confirmed this in this repo's smoke tests, 2026-04-26). U5 may have moved enforcement from "warn + load" to "warn + sandbox" or "warn + degrade." A sandboxed plugin loses access to some VCOM interfaces, but the call sites in our code still try them — null deref or unmapped-memory access → SEH/BSOD class.
- **Predicts:** "Unknown Developer" dialog still shows; bridge starts fine; first `gSDK->GetDrawingHeader()` or first `IPythonScriptEngine::ExecuteScript` call is the crash trigger.
- **Discriminator test:** generate the Plugin Credentials file (per VW dev docs), reload the plugin, retest. If the "Unknown Developer" dialog goes away **and** the crash stops, this is it.

### H2 — VCOM interface table drift in U5 (medium prior)
- **Mechanism:** A point release added a method to one of the interfaces we hold a pointer to (`IPythonScriptEngine`, `IVectorScriptEngine`, base `gSDK` ISDK), shifting later vtable slots. Our plugin built against the 2026.0 SDK calls into the wrong slot on U5.
- **Predicts:** crash happens on a *specific* SDK call, not on plugin load. The crash signature (which method was being entered) points at which interface drifted. Symptom would correlate with VW operations and not with plugin lifecycle.
- **Discriminator test:** build the plugin against the **2026.5 SDK** (if Nemetschek has released a refreshed SDK alongside U5) and retest. If the rebuild fixes it, ABI drift confirmed.

### H3 — IPythonScriptEngine threading/init contract changed (medium prior)
- **Mechanism:** Our `FORK_NOTES.md` already documents an init-order SEH that required deferring auto-start to the 4th `plugin_module_main` call. If U5 changed when the Python runtime is ready, the deferred-by-4 heuristic could now be too early (crash on first run_script) or too late (no functional change but worth ruling out).
- **Predicts:** the "no active document" guard already in `BridgeCore::HandleCommand` catches some of this. Crash would specifically be on the *first* `run_script` after a fresh VW launch, with the document open.
- **Discriminator test:** start the bridge **manually via the palette toggle**, not auto-start, then immediately call `run_script` with `print('hi')`. If manual start + first run_script crashes but later run_scripts don't, init-order is implicated.

### H4 — Morpholio Trace integration claims a previously-free resource (low prior, but worth noting)
- **Mechanism:** U5 added new background services / threads / sockets for the Trace round-trip. If any of those bind a fixed port or pipe, our `127.0.0.1:27231` listener could now be racing or conflicting with VW-internal services.
- **Predicts:** bridge would fail to bind on launch with `bind(): EADDRINUSE`, not a crash. Easy to falsify — `netstat -ano | findstr 27231` before starting the bridge.
- **Discriminator test:** check port availability before bridge start; if anything other than our process holds it, we have a collision.

### H5 — Driver-level regression unrelated to plugin (low prior, but explains BSOD)
- **Mechanism:** the forum reports specifically mention BSOD — those are kernel-mode, not user-mode crashes. A user-mode plugin can't *directly* cause a BSOD; only a driver or kernel-callable resource can. Candidates: licensing sentinel/HASP driver, GPU driver path used by Morpholio Trace export, file-watcher kernel hook.
- **Predicts:** crashes happen even with all third-party plugins disabled.
- **Discriminator test:** disable all third-party plugins via VW settings; reproduce the BSOD. If it still happens, our plugin is innocent and the issue is in VW itself.

## 3. Triage protocol (to run when next at the VW2026 machine)

**Goal:** discriminate between H1–H5 with the minimum number of VW launches.

### Step 0 — Capture the baseline state
1. `%APPDATA%\Nemetschek\Vectorworks\2026\Logs\` — copy any crash logs since U5 was installed. The `LastShutdown=` line in the most recent log is the single most informative signal (`Normal` = clean exit, `Crash` = SEH, `Hung` = deadlock).
2. Note the exact VW build number from `Help → About Vectorworks`. Match against the U5 build number in the Vectorworks portal release notes.
3. Confirm: is the licensing sentinel/HASP driver on the latest version? (Sentinel updates are independent of VW updates and have caused BSODs historically.)

### Step 1 — Does our plugin even start cleanly?
1. Launch VW2026. Dismiss the "Unknown Developer" dialog (Enable + Continue).
2. Open the MCP Bridge palette (Window → Palettes → MCP Bridge).
3. Click Start. Expect the status dot to go green and the alert to read `MCP Bridge started at 127.0.0.1:27231`.
4. From a shell, run: `vectorworks-mcp-server.exe --vw-version 2026` — should log `Vectorworks bridge: connected`.

**If Step 1 fails:** the regression is in plugin load itself. Strong signal for H1 (credentials) or H4 (port collision). Skip to Step 5 (credential file) before continuing.

### Step 2 — Does the simplest tool work?
1. From Claude Code (or directly via TCP): call `ping`. Expect `pong`.
2. Call `get_drawing_info` against an open document.

**If Step 2 fails:** the regression is in basic VCOM access (`gSDK->GetDrawingHeader`, `FirstMemberObj`, etc.). Strong signal for H2 (VCOM drift).

### Step 3 — Does Python script execution work?
1. With an open document, call `run_script` with `print('hello')`. Expect `{stdout: "hello\n", stderr: "", error_code: 0, success: true}`.
2. Call `run_script` with `import vs; print(vs.GetFName())`.
3. Call `run_script` with `raise Exception('test')` — expect structured failure, **not a crash**.

**If Step 3 crashes VW:** the regression is in `IPythonScriptEngine`. Strong signal for H3 (init contract) or H2 (interface drift specifically on the Python engine).

### Step 4 — Cross-check with a third-party plugin
1. Disable our MCP Bridge plugin (rename the `.vlb` out of the Plug-ins folder; relaunch).
2. Try to reproduce the original crash with the third-party plugin only.

**If the third-party plugin still crashes:** our plugin isn't the trigger. Either the third-party plugin has the same H1/H2/H3 issue, or it's H5 (driver-level).

**If the third-party plugin works fine with ours removed:** there's something specific about our plugin that's triggering the regression — or about how the two plugins interact (port? thread? VCOM ref counts?).

### Step 5 — Generate plugin credentials (closes H1)
- Follow the VW2026 dev docs to register as a developer, obtain a `.vwplugincred` file, and ship it alongside the `.vlb`.
- Even if H1 isn't the root cause, this is on the to-do list per `FORK_NOTES.md` and a precondition for ruling out credential-related causes.

### Step 6 — Rebuild against the 2026.5 SDK (closes H2)
- Check `https://www.vectorworks.net/en-US/support/custom/sdk/sdkdown` for an SDK refresh dated after U5's release (2026-05-12).
- If present, point `VWSDKRoot` at it, rebuild Release|x64, redeploy `.vlb`. Re-run Steps 1–3.

## 5. What NOT to do yet

- **Don't** patch around the symptom in `BridgeCore.cpp` blindly (adding more guards, more `if (!gSDK)` checks). Without knowing whether H1, H2, or H3 is the cause, defensive patches risk masking the real signal and making the next regression harder to diagnose.
- **Don't** invest in the L2 templated-tools work (see `docs/coverage-spec.md`) until the plumbing is known-good on U5. Adding more `run_script`-routed tools on top of a broken `IPythonScriptEngine` path just multiplies the failure surface.
- **Don't** assume Gantry's failure mode is the same as our plugin's failure mode without confirming both crash in the same call site. They may share a root cause (H1/H2/H5) or fail independently for unrelated reasons.
